Este documento consolida o planejamento técnico do Backend para o Portal Reconcilia. FT-01 | US-BE-01

Solicitação de Acesso via Código OTP

Prioridade Crítica

Como API do Portal Reconcilia, quero receber o CPF do usuário, validar sua existência cadastral no Bureau de Crédito, gerar uma senha de uso único (OTP) criptograficamente segura com validade limitada e enviá-la via canal cadastrado (SMS ou E-mail), para iniciar o processo de identificação confidencial.

Contrato de Endpoint

POST /api/v1/auth/login-request
Request Body (JSON) 
{
  "cpf": "12345678901",
  "channel": "SMS" // SMS ou EMAIL
}
Response 200 OK 
{
  "session_id": "sess_99210a4f-8321-4d1a-9ee0-d02fa7c8fa11",
  "masked_contact": "(11) 9****-2105",
  "channel_sent": "SMS",
  "expires_in_seconds": 300
}

Regras de Validação e Negócio

  • Validação de CPF: Validar o algoritmo matemático dos dígitos verificadores (módulo 11). Se inválido, retornar HTTP 400 Bad Request.
  • Geração do Código OTP: Gerar um número inteiro aleatório de 6 algarismos utilizando SecureRandom e armazenar seu hash criptografado (SHA-256) em cache MongoDB/Redis com tempo de vida limitado a 5 minutos.
  • Controle de Vazão (Rate Limiting): Permitir no máximo 1 solicitação de código de login por CPF a cada 60 segundos. Se violado, retornar HTTP 429 Too Many Requests.
FT-01 | US-BE-02

Validação de OTP e Emissão de Token JWT

Prioridade Crítica

Como API do Portal Reconcilia, quero validar o código OTP enviado pelo usuário em sua respectiva sessão temporária de login, e caso correto, emitir um token JWT assinado para assegurar o tráfego do usuário sob criptografia e sigilo financeiro.

Contrato de Endpoint

POST /api/v1/auth/verify-otp
Request Body (JSON) 
{
  "session_id": "sess_99210a4f-8321-4d1a-9ee0-d02fa7c8fa11",
  "otp_code": "482015"
}
Response 200 OK (JWT setado no Cookie HttpOnly) 
{
  "authenticated": true,
  "user": {
    "cpf": "12345678901",
    "name": "Ana Maria de Souza",
    "last_access": "2023-11-20T10:15:30Z"
  }
}

Regras de Validação e Negócio

  • Bloqueio contra Brute Force: Limitar o número de tentativas de validação do código OTP a no máximo 3 vezes consecutivas. Caso ultrapasse, expirar permanentemente a sessão e retornar HTTP 401 Unauthorized com payload de erro descritivo.
  • Criação de Sessão JWT: O token JWT emitido conterá claims de identificação (sub = CPF, roles = ["CONSUMER"]) e será assinado com chaves privadas RSA-256 geradas dinamicamente no Secrets Manager.
  • Armazenamento Seguro: O token JWT de acesso seguro será injetado no cabeçalho de resposta através de cookies com flags HttpOnly, Secure e SameSite=Strict para mitigar ataques XSS e CSRF.
FT-02 | US-BE-03

Consulta e Consolidação de Dívidas Elegíveis

Prioridade Alta

Como API do Portal Reconcilia, quero receber o token JWT do usuário, extrair o CPF de forma criptograficamente segura, consultar a base local de restrições de crédito integradas e as APIs dos credores parceiros, aplicando as regras de descontos de partida para exibir a listagem unificada de pendências.

Contrato de Endpoint

GET /api/v1/debts
Requer Cabeçalhos (Headers) 
Authorization: Bearer [JWT_TOKEN]
Response 200 OK 
{
  "summary": {
    "total_original_value": 3100.00,
    "total_discounted_value": 1150.00,
    "total_savings": 1950.00,
    "number_of_debts": 2
  },
  "debts": [
    {
      "debt_id": "deb_abc123",
      "creditor_name": "Banco Alpha",
      "original_value": 2500.00,
      "current_value_with_interest": 2850.00,
      "minimum_negotiable_value": 850.00,
      "discount_percentage": 66,
      "days_overdue": 320,
      "status": "ELEGIBLE_FOR_NEGOTIATION",
      "contract_number": "CTR-99481-A"
    },
    {
      "debt_id": "deb_xyz789",
      "creditor_name": "Telefonia Beta",
      "original_value": 600.00,
      "current_value_with_interest": 600.00,
      "minimum_negotiable_value": 300.00,
      "discount_percentage": 50,
      "days_overdue": 120,
      "status": "ELEGIBLE_FOR_NEGOTIATION",
      "contract_number": "TEL-88122-B"
    }
  ]
}

Regras de Validação e Negócio

  • Autenticidade e Claims: Se o token JWT não for enviado ou estiver expirado, retornar HTTP 401 Unauthorized de forma imediata.
  • Consolidação de Dados Resiliente: O backend consulta a base local de restrições (sincronizada via arquivos batch diários dos credores) de modo prioritário. Se a API de algum credor parceiro estiver online para consulta síncrona de saldo em tempo real, aplicar as taxas atualizadas; caso contrário, utilizar o saldo histórico gravado localmente para manter a disponibilidade.
  • Elegibilidade de Dívida: Apenas dívidas com status ELEGIBLE_FOR_NEGOTIATION devem ser listadas. Dívidas já ajuizadas ou em processo jurídico avançado não devem aparecer no portal de autoatendimento.

Consulta de Pontuação de Score

Prioridade Alta

Como API do Portal Reconcilia, quero buscar de forma síncrona a pontuação de score de crédito associada ao CPF autenticado no JWT diretamente na API do Core do Bureau de Crédito, retornando a pontuação e sua classificação de risco para exibição imediata no frontend.

Contrato de Endpoint

GET /api/v1/score
Response 200 OK 
{
  "score": 645,
  "classification": "GOOD",
  "updated_at": "2023-11-21T18:40:00Z"
}

Regras de Validação e Negócio

  • Isolamento de Timeout: A chamada de integração com o barramento do Bureau Core para leitura do Score de Crédito terá timeout estrito configurado para 2.0 segundos. Caso o Core apresente lentidão, responder com o score em cache local histórico ou definir o valor de score como nulo, garantindo que o resto do carregamento das dívidas não seja impactado.
  • Mapeamento de Faixas de Score: Aplicar o algoritmo de categorização do score em conformidade com as regras de negócios: 0 a 300 (LOW), 301 a 500 (REGULAR), 501 a 700 (GOOD) e 701 a 1000 (EXCELLENT).
FT-03 | US-BE-05

Motor de Simulação Dinâmica de Acordo

Prioridade Alta

Como API do Portal Reconcilia, quero receber as variáveis de renegociação propostas pelo devedor (valor da entrada e número de parcelas), validar as permissões financeiras junto às regras cadastradas por credor, e retornar a simulação completa persistindo-a de forma rápida em cache NoSQL MongoDB com validade TTL de 15 minutos.

Contrato de Endpoint

POST /api/v1/negotiations/simulate
Request Body (JSON) 
{
  "debt_id": "deb_abc123",
  "installments_requested": 12,
  "down_payment": 100.00
}
Response 200 OK 
{
  "simulation_id": "sim_88491823",
  "debt_id": "deb_abc123",
  "original_value": 2500.00,
  "discount_applied": 1500.00,
  "total_negotiated_value": 1000.00,
  "installments": 12,
  "down_payment": 100.00,
  "installment_value": 75.00,
  "interest_rate_monthly": 1.5,
  "savings": 1500.00,
  "due_date_first_installment": "2023-11-25",
  "expires_at": "2023-11-21T19:05:00Z"
}

Regras de Validação e Negócio

  • Validação de Parcela Mínima: Rejeitar a simulação e retornar HTTP 422 Unprocessable Entity caso o valor da parcela calculado fique abaixo de R$ 50,00, informando o erro no payload de erro estruturado.
  • Lógica de Juros Simples/Compostos: O motor de cálculo de backend deve aplicar juros compostos ou juros simples, a depender da política parametrizada do credor da dívida, incidindo sobre o saldo devedor amortizado pelo valor de entrada (down_payment).
  • Persistência Volátil (MongoDB TTL): A simulação gerada de forma provisória é salva em uma coleção com índice expireAfterSeconds de 900 segundos (15 minutos). Isso impede que simulações rascunho descartadas consumam armazenamento físico no banco PostgreSQL.
FT-04 | US-BE-06

Confirmação e Criação do Acordo de Pagamento

Prioridade Crítica

Como API do Portal Reconcilia, quero validar o ID de simulação ativo no MongoDB, assegurar o consentimento explícito do termo de confissão de dívida, cadastrar o acordo de forma transacional (PostgreSQL) com status "AWAITING_PAYMENT", e solicitar a emissão do QR Code Pix do pagamento diretamente na API do Gateway, para formalizar o encerramento da simulação.

Contrato de Endpoint

POST /api/v1/agreements/confirm
Request Body (JSON) 
{
  "simulation_id": "sim_88491823",
  "payment_method": "PIX",
  "terms_accepted": true
}
Response 201 Created 
{
  "agreement_id": "agr_559102",
  "status": "AWAITING_PAYMENT",
  "payment_method": "PIX",
  "pix_copia_e_cola": "00020101021226870014br.gov.bcb.pix2565...",
  "pix_qr_code_url": "https://images.bureau.com.br/qrcodes/agr_559102.png",
  "expires_at": "2023-11-21T20:05:00Z",
  "amount_due": 100.00
}

Regras de Validação e Negócio

  • Validação de Consentimento Legal: Se o parâmetro terms_accepted for falso, recusar a operação retornando HTTP 400 Bad Request com mensagem legal específica.
  • Garantia de Transação ACID: A inserção do acordo na tabela tb_agreements e o parcelamento na tabela tb_installments devem ocorrer dentro de uma transação do banco PostgreSQL (@Transactional). Qualquer falha de gravação ou timeout com o banco deve desfazer as operações (Rollback).
  • Geração do Pix via Gateway: Consumir a API síncrona do Gateway Bancário parceiro enviando o valor negociado e obter a chave do Pix. O Pix de entrada terá vencimento estipulado para 1 hora. Caso seja boleto, o vencimento mestre será de 3 dias úteis.
FT-04 | US-BE-07

Webhook de Recebimento de Pagamento do Gateway

Prioridade Crítica

Como API do Portal Reconcilia, quero escutar as chamadas HTTP seguras do webhook do Gateway de Pagamentos contendo os dados de liquidação da transação, conferir a assinatura digital e o token de segurança, atualizar transacionalmente o status do acordo para "PAID", e enfileirar o evento no RabbitMQ para conciliação física.

Contrato de Endpoint

POST /api/v1/payments/webhook
Request Body (JSON) 
{
  "event": "payment.succeeded",
  "timestamp": "2023-11-21T19:10:15Z",
  "signature": "sha256=abcdef1234567890abcdef...",
  "data": {
    "transaction_id": "tx_bc881920aa",
    "agreement_id": "agr_559102",
    "payment_method": "PIX",
    "amount_paid": 100.00,
    "paid_at": "2023-11-21T19:10:12Z"
  }
}
Response 200 OK 
{
  "status": "PROCESSED",
  "received_at": "2023-11-21T19:10:16Z"
}

Regras de Validação e Negócio

  • Assinatura Digital de Segurança: O cabeçalho de requisição conterá um hash criptografado em assinatura digital (X-Hub-Signature-256) calculado pelo Gateway utilizando o algoritmo HMAC-SHA256 com segredo compartilhado. O backend do portal deve recalculá-lo e validá-lo; se divergente, retornar HTTP 403 Forbidden.
  • Idempotência Transacional: Garantir a idempotência do webhook para evitar dupla quitação se o mesmo evento de sucesso for reenviado pelo Gateway. Tratar isso por meio de uma trava otimista no banco PostgreSQL ou validação de chave única de pagamento cadastrada.
  • Event Sourcing (Mensageria): Assim que o status do acordo for atualizado para PAID de forma transacional, publicar imediatamente a mensagem JSON AgreementPaidEvent no exchange ex.agreement.events do RabbitMQ com chave de roteamento agreement.paid.

Worker Assíncrono de Conciliação e Baixa

Prioridade Crítica

Como Microsserviço Worker de Conciliação do Portal Reconcilia, quero consumir as mensagens da fila de sucesso de acordos do RabbitMQ, atualizar o status restritivo do devedor no Bureau Core para garantir o Score Boost, e notificar os sistemas internos do credor externo sobre o acordo quitado, para cumprir o SLA mestre de 24 horas úteis.

Especificação de Mensageria (AMQP)

Exchange ex.agreement.events
Queue q.agreement.paid
Payload do Evento (JSON) 
{
  "event_id": "evt_bc9910aa-ff02-41aa-8812-d02fa7c8faef",
  "event_type": "AGREEMENT_PAID",
  "timestamp": "2023-11-21T19:10:16Z",
  "payload": {
    "agreement_id": "agr_559102",
    "cpf": "12345678901",
    "debt_id": "deb_abc123",
    "amount_paid": 100.00,
    "creditor_identifier": "cred_alpha_bank"
  }
}

Regras de Validação e Negócio

  • SLA de Limpeza do Nome (24 horas): O worker de conciliação executa em background de forma isolada do fluxo HTTP principal. Ao receber a mensagem, o worker chama a API interna de negativação do Bureau Core para remover o registro restritivo do CPF devedor de forma priorizada.
  • Atualização Assíncrona do Credor: O worker efetua uma requisição de conciliação comercial à API externa de cobrança do credor parceiro correspondente. Se a API externa estiver fora do ar, reter a mensagem na fila de retentativa e não realizar o Ack.
  • Resiliência de Integração (Dead Letter Exchange): No caso de falha de conexão persistente com a API do credor, o RabbitMQ deve reencaminhar a mensagem para uma fila com política de retentativa exponencial (Retry Exponential Backoff) em intervalos progressivos. Se após 5 tentativas consecutivas o erro persistir, o evento é movido para a Dead-Letter Queue (q.agreement.paid.dlq) e um alerta prioritário de suporte técnico é gerado no console de monitoramento.
